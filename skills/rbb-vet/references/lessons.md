# 验题常见的坑（通用）

从已发布的 8 道题和 2026-11 一批新题的验题里整理出来，只留和具体题无关的部分。规范见 [protocol.md](protocol.md)，展开的做法见 [guide.md](guide.md)。

## 判卷只准备一次，处处复用（参考包）

- 启动准备（参考记录、轨迹、冻结的 σ、计时参考、对照的证据）按“参考包”的边界拆：和机器无关的部分只做一次，打成包，所有机器共用；每台机器只重做便宜的验证（参考记录一次逐位比对、参考计时一次落在 band 里）。`vetkit/` 的 `refpack.py` 就是这套机制的单机版。
- 包按 key 寻址：任务、判卷哈希、镜像 digest、GPU 型号、卡数、驱动、准备版本。任何一个变了就是另一个包，不悄悄替换。
- 判卷一改，以它的哈希为 key 的包就失效。只有包里的文件不受影响时才能换 key，并留下记录。
- 建包要在独占、安静的整机上做：包冻结的参考计时决定了 agent 自己 check 的门槛，建包时测得的参考波动超过上限就不发布，重建。

## 计时

- 窗口里不能有按形状首次触发的东西（Triton autotune、`torch.compile`、cuDNN 按序列长度编译图）。warmup 要跑计时那几步的同样数据，或者先预跑一次填满缓存、计时的那次从缓存的拷贝启动。在判卷里报告每个窗口里编译 / autotune 花了多少秒。
- 一对参考计时相差 > 3% 就再测一对，最多 3 对，还不行就标 `timing_spread_flag`。计时运行崩了就重测，不要直接让准备失败。
- 计时运行也记 loss，和参考的对一下：能抓到别的门漏掉的偏差。
- 计时时这台机器上不 build、不扫网络盘（`find /`、`du`）、不下载、不跑别的 GPU 任务。扫一次网络盘就足以毁掉一对计时。
- 绑核：GPU、绑到的 CPU、内存要在同一个 NUMA 节点上。每张卡分它所在 NUMA 节点上等份的核（`vetkit/bin/run_trial.py --cpus auto`）。线程数不用另外限制，3% 重测规则能吸收偶尔的离群值。
- 随机策略要固定：参考配方里的随机路由、随机调度（例如请求随机分给几个引擎）换成确定性的（例如轮询），否则它本身就是计时噪声。
- 同一台机器另一半释放大块显存时，驱动全局锁会让一次计时卡住 10 秒以上：终判各侧取最快、可补测，见规程补充 D1。

## 统计门

- 跑**生产配置**（就是被计时的那套），逐位一致的候选也跑。确定性模式下判了、生产配置里换了 kernel 的情况（例如只在生产路径上用的注意力 kernel）就是这样漏掉的。
- 端点优先取第 0 步附近的统计量：非逐位的更新之后，差值的尾部很重。
- 只靠比值的规则拦不住很小的系统偏差，加有符号的配对检验；不逐位的参考用 N1：配对噪声、按数据集的 3σ、更新方向的余弦，再加一个 lr×1.02 的对照。
- 采样类的门用参考包里冻结的基准，不用单次启动冻结的几个窗口（规程补充 C6）。
- 多小时的准备之前，先跑一个几分钟的探针：例如把某条规则的基线重放两次，确认它非零、确实测到了它要测的东西。基线为 0 会把统计规则悄悄变成“只收逐位”。
- 统计规则的容差要用参考自己真实会遇到的变化（例如重新分批）来标定，不要只用同一批次重放：有的模型对分块边界很敏感，同批重放的容差会把合法的重新分批全部拒掉。

## 对照

- 每道门至少一个必拒对照，要让门**判错**（INCORRECT），不能让程序崩（ERROR）。
- 改动要落在配方真正跑到的代码路径上：改一条没被调用的代码（例如没用到的那个 loss 分支），候选照样会以 N1 通过，什么也没测到。
- 对照在两个 GPU 半边上并行跑，不计时。
- 合法改写被拒时先查谁错了（规程补充 C2）：有时是“合法”改写其实改变了输出。

## RNG 和确定性

- RNG 指纹要忽略库自己的簿记，例如 Triton 的缓存临时文件名从 Python 的全局 random 取数。
- 有 RNG 的题（扩散噪声、dropout）：判卷要么自己提供噪声，要么只比和 RNG 无关的量。
- 没有确定性 backward 的注意力 kernel（FA3、cuDNN SDPA）在确定性模式下要换成同精度、有确定性实现的 kernel，题面写明，否则计时的 kernel 和被判的不是同一个。

## 镜像和启动

- 镜像源拒绝的基础镜像：先拉成 OCI 归档再 `docker load`；本地 load 的基础镜像，Harbor 构建时要给一个空的 `DOCKER_CONFIG`，否则它会去 registry 校验。
- `set -o pipefail` 下不要写 `cmd | head`：head 先退出，cmd 收到 SIGPIPE 返回 141。
- Harbor 的 egress 探测有 30 秒超时：几个 trial 同时启动会失败，错开启动。
- 准备失败时 Harbor 0.24 会一直轮询健康检查到 start period 结束（可能好几个小时）：`vetkit/bin/run_trial.py` 发现主容器已退出就保存日志、停掉 Harbor。
- 判卷正被用的时候不改判卷目录：它是冻结输入，一改，正在跑的 check 全部 ERROR。
- 模板里的几个坑（GPU 锁权限、僵尸进程、`/tmp` 权限、slim 镜像的 python 路径、forward-compat 库、Compose `!reset`）见规程补充 C9。

## 机器

- 不在共享机器上做准备：别人的任务中途占了卡，几个小时的准备就白做了。用卡之前看 `nvidia-smi`，有调度器就经调度器拿卡，没有就在机器上留一个占用说明（谁、做什么、哪几张卡、到什么时候），用完删掉。别人的任务、容器一律不碰。
- 纯 CPU 的题照样占一个 NUMA 半边（它的核），计时期间这半边的卡也不要给别的计时任务。
- ncu 读不了硬件计数器（`ERR_NVGPUCTRPERM`，或者驱动设了只有管理员能用）时直接跳过，报告里写一句；T1 只靠微基准。
