# RSI-Infra Bench 验题规程（A–E）

> 本文是验题的**规范**：时间预算、硬规则、每段的检查和阈值、打分卡格式都以它为准。
> 正文（到“最后交给我”为止）是 bench 负责人 2026-11-22 定稿的规程，原样保留，写给做验题的 agent 或人看。文中的“我”指**题目负责人（owner）**：自己验题的贡献者就是你自己；替 bench 验题时是 bench 的维护者。
> 文末的《实践补充》是 2026-11-23 到 11-25 验多道新题时定下的通用规则，和正文一样有效；两者冲突时以补充为准（补充只收紧或说清楚，不放宽）。
> 怎么一步步做见 `guide.md`，常见的坑见 `lessons.md`，工具见 `../scripts/` 和仓库的 `vetkit/`。

把一个训练仓库做成 RSI-Infra Bench（https://github.com/DAGroup-PKU/ResearchBoost-Agent 的 bench 分支）的一道题，并判断它该不该进 bench。按 A–E 五段做，目标是尽快出结论。

【时间预算】总共约 3 天墙钟：
- A ≤ 2 小时；
- B ≤ 半天；
- C 小题 ≤ 1 天，大题 ≤ 2 天；
- D 是 10 小时，所有格子同时跑；
- E ≤ 2 小时。

某一段超出预算，就停下来告诉我卡在哪里。

【怎么省时间】
- 一开始就一次问完我要定的所有事，包括 D 段用哪个（或哪些）模型、跑在哪些卡上。之后一路往下做。
- 只在三种情况下停下来等我：某项检查 FAIL；需要我拍板；超出时间预算。
- 任何长运行之前，先用最小计划（1 步 warmup、1 步窗口、2 步轨迹）把每条路径跑通。
- 不计时的运行（变异、合法改写、记录）分组卡并行跑。计时只在整机空闲时跑。
- 前面的段 FAIL 就停，不往后做。

【输入】下面几项我没给的，先看环境再一次问完，每项给出你的推荐值：
- 仓库和 commit；
- 上游文档里的训练命令；
- 题名；
- 可用的 GPU；
- 工作目录（放在我的仓库外面）；
- D 段用哪个模型和 agent（一个就行，有多个也可以列出来），以及卡位。

看环境就是查这几样：nvidia-smi、df -h、docker、harbor、nsys、ncu、有没有 root。

【硬规则】
1. agent 能看到的东西（instruction.md、镜像里的所有文件）里不写目标加速比、已有成绩、热点、开关名、优化思路、别的硬件。验题数据只放 vetting/<题名>/，不进 tasks/，也不进镜像。
2. 题面不写任何时长。
3. 判卷标准不为放过某个候选而放宽。只有参考自己都做不到时才放宽，并写明原因。
4. 计时时机器上不做别的：不 build，不扫网络盘，不跑别的 GPU 任务。只用分给你的 GPU 和目录，只删自己建的东西。
5. 只用公开的代码、权重、数据，每个都钉住 revision 和 checksum。
6. 每个数字写清出处（命令、日志路径），并标明是实测还是估计。

【A 案头（不用 GPU，≤ 2 小时）】
- 和输入一起问我定这些：
  - 命令：必须是上游文档里的；
  - 卡数和缩放：每卡负载和上游一样，global batch 等比缩小或用梯度累加补齐；
  - 计时单位：训练题用秒/update，RL 题用秒/step；
  - 精度下限：等于参考的精度；
  - 收 N0（逐位一致），还是 N0 + N1（统计等价）；
  - 并行布局、重算、通信方式能不能改；
  - 有两种读法的规则：逐条请我定死。
- 记下三样：
  - 专家锚点：上游的性能 PR、speedrun 记录、已知的快版本；
  - 瓶颈类型：gemm / memory / comm / host / irregular；
  - 要在题面禁掉的已公开快版本。
- 准入：用的是上游命令；全部公开；没有没定死的歧义。

【B 上限和基线强度（≤ 半天）】
1. 测参考：
   - 跳过 warmup，取 3 个固定窗口测每单位时间，多卡取最慢的那张卡；
   - 同一配置跑两次，A/A = |a − b| / 均值。
2. 分阶段 profile：
   - torch.profiler（record_shapes=True）跑几步：拆出前向、反向、优化器、通信、主机各阶段，抽出 GEMM 形状；
   - 有 nsys 就用它看时间线；
   - ncu 只在装了、且能读硬件计数器（root，没有 ERR_NVGPUCTRPERM）时用，否则跳过，在报告里写一句；用的话只抽最重的几个 kernel，加 --clock-control none。
3. 每个阶段算三样：
   - 各精度的 FLOPs，用 FlopCounterMode 核对；
   - 融合口径下最少的 HBM 字节：权重和输入读一次、输出写一次，存下的激活和优化器状态照算；
   - NVLink 字节。
4. 算 T0：T0 = Σ 阶段 max(FLOPs / 手册峰值, 字节 / 手册 HBM 带宽, 通信量 / 手册 NVLink 带宽)。H100/H200 SXM 的手册值：
   - BF16 989.5 TFLOP/s，FP8 1979，TF32 494.7，FP32 67；
   - HBM 3.35 / 4.8 TB/s；
   - NVLink 每方向 450 GB/s。
5. 算 T1：同一个公式，峰值换成实测值。
   - 只测覆盖 ≥ 80% GEMM 时间的那几个形状：先连跑几秒，等时钟稳定，再取 torch.matmul 和 torch.compile(mode="max-autotune") 里较快的那个；
   - 注意力：测 SDPA flash 后端，能装上 FA3 时也测；
   - HBM：用大拷贝测带宽；
   - 通信：按 nccl-tests 的 busbw 口径；
   - 只收 N0 的题：GEMM 按参考 kernel 的实测时间算。
6. 开关阶梯：只用规则允许的现成开关，最多叠 5 个，每个测一次，记下最好组合的加速比 L。可选的开关例如 torch.compile、fused 优化器、CUDA graph、注意力后端、NCCL bucket、dataloader worker 数、题目允许时的 TF32。
7. 估一次完整 check 要多少分钟。
- 准入（不过就停）：
  - T_ref / T1 ≥ 2；
  - ln L / ln(T_ref / T1) ≤ 1/3。超过时，问我是把这些开关并进参考，还是拒掉这道题；
  - A/A ≤ 3%；
  - 完整 check ≤ 60 分钟。

【C 打包和验判卷（小题 ≤ 1 天，大题 ≤ 2 天）】
- 选模板：克隆 bench 分支，照最像的那道题抄结构。
  - nanochat：最简单；
  - llava / yoco：带 preparation pack；
  - bagel_sft：配方数据走不到的分支，单加一道门；
  - slime_grpo / slime_opd：RL，用 token forcing；
  - gaussian_splatting：按整次运行计时。

  判卷的通用比对代码照搬 ResearchBoost-Agent 主分支的 numerics/，先读它的 docs/judge.md。
- task.toml：
  - artifacts 写 /submission/<题名>、/submission/switches.json、/opt/candidate-env；
  - [agent]：user = "agent"，network_mode = "public"，timeout_sec = 36000；
  - [verifier]：environment_mode = "shared"，user = "root"，network_mode = "no-network"；
  - 健康检查：test -f /run/researchboost-ready。

  写完跑 python scripts/validate_config.py tasks/<题名>。
- 判卷的几道门：
  - gate 0 结构：setup 不变；数据探针确认样本和参考一致。
  - gate 1 收益：
    - 固定窗口计时，最终评测按 参考 → 候选 → 参考 测；
    - 门槛 max(1.02, 1 + 2 × 参考自己的波动)；
    - 参考自己超出波动带 → INVALID。
  - gate 2 逐位：确定性模式下记录几步，exact items 逐项比，张量逐位一致 → N0。
  - gate 3 统计：
    - 用生产配置跑一个冻结种子的短轨迹，每个端点满足 |候选 − 参考| ≤ 3σ，σ 是参考 6 个种子之间的标准差；
    - 只靠这条拦不住 lr×1.02 时，再加有符号的配对检验。
  - 配方数据走不到的分支：单独加一道门。
- 启动准备：
  - 参考在确定性模式下记录两次，必须逐位一致；
  - 跑 6 个种子的轨迹，冻结 σ；
  - 参考自己的 quick check 应为 PASS，final 应为 no_benefit。
- 必拒变异（并行跑）：每个都要让门判错，而不是让程序崩溃。
  - lr×1.02；
  - 去掉一个 loss 项的梯度；
  - 少一个 micro-batch；
  - 改数据顺序；
  - 改 setup；
  - 配方走不到的分支改错（有这种分支时）。
- 必过的合法改写（并行跑）：
  - 3 种各跑 1 次，一次都不能被拒；
  - 例如：换 micro-batch 和累加次数、融合 norm、分块算 CE、换规约顺序；
  - 用这几次的 z 值（偏差 / σ）估误拒率：模拟 6 个参考种子，加一个和种子 0 相关为 ρ 的候选，数 |d| > 3σ̂ 的比例；各端点按独立合成，整体要 ≤ 1%。
- 泄漏：agent 能看到的所有文件先 grep，再人读一遍。
- 冒烟：harbor run -p tasks -i <题名> -a nop -n 1，reward 应为 0。
- 准入：必拒的全拒；必过的 0 次被拒；预测误拒 ≤ 1%；泄漏为 0；nop 为 0。

【D pilot（10 小时；多格时并行）】
- 命令：harbor run -p tasks -i <题名> --env-file researchboost.env -a <agent> -m <model> -n 1。
- 用我给的模型跑，至少一格完整的 10 小时。
- 我给了多个模型：每个一格，同时跑。
- 卡够的话，再给其中一个模型跑一个复本，用来看噪声。
- 每个非 PASS 的格子都要归因：
  - model：模型真改错了；
  - judge：合法改写被拒，回到 C；
  - infra：修好后重跑。
- 通过的提交也要看：加速是不是钻了空子。
- 算 h = ln(加速比) / ln(T_ref / T1)。
- 准入：
  - 最好成绩的 h 在 20–80% 之间（高于 80% 是饱和，低于 20% 先查 T1 和规则）；
  - 没有归因为 judge 的失败，也没有没归因的失败；
  - 最好成绩 < 1.3× 时，报告里说明原因：可能是题的成绩区间太窄，也可能是这个模型偏弱；
  - 跑了多格时再看两条：复本之间的差 < 模型之间的差；模型的先后顺序和排行榜一致。

【E 收尾（≤ 2 小时）】
- 最好的提交用 final 重判 2 次，都要 PASS；
- 记下判卷哈希、镜像 digest、上游 commit；
- 不 push，不开 PR，等我看。

## 实践补充（2026-11-23 至 11-25，通用规则）

这些规则来自若干道新题的验题。每条写“规则”和“为什么”。编号按段，引用时写“补充 B2”这种。

### A 案头

- **A1 精度规则写到具体部分，点名开关。** 题面写“fp32 的计算可以用 bf16、fp16 或 TF32”这类笼统的话，而参考里有对精度敏感的 fp32 计算（例如 loss 里某一项依赖的一段 fp32 矩阵乘），一个按题面算合法的改写（整体打开 TF32）就会被统计门拒掉，题面和判卷对不上。
  - 规则：精度下限按**部分**写：哪些部分保持参考精度（点名到模块或计算段），哪些部分可以降到哪一档。
  - 会整体改变 fp32 矩阵乘精度的开关逐个点名禁止或允许：`torch.backends.cuda.matmul.allow_tf32`、`torch.backends.cudnn.allow_tf32`、`torch.set_float32_matmul_precision`、`NVIDIA_TF32_OVERRIDE` 这类环境变量。
  - B 段开关阶梯里的 TF32 一档、C 段合法改写里的精度类改写，都要和这条一致。发现不一致时先改题面（收窄），再跑对照。
- **A2 计时窗口里不能有按形状首次触发的编译。** 参考配方本身在计时窗口里编译或调优（某个后端每遇到一个新形状就编译 / autotune 一次）时，参考的时间里大半是编译，T_ref 虚高，题就变成“关掉编译”。处理：A 段请 owner 预先授权“把只影响首次使用、不改数值的设置并进参考”，B 段发现后直接并进参考，报告里写明。
- **A3 显存上限按碎片少的分配器量。** 题面有“显存峰值不超过参考 × k”这类规则时，参考峰值要用碎片少的分配器设置（例如 `expandable_segments`）量。默认分配器的缓存池能让峰值虚高一倍，上限就拦不住它本来要拦的东西。两种读法给出两个上限，属于 A 段要定死的歧义。
- **A4 纯 CPU 的题。** 计时单位用整次运行的墙钟；T0/T1 按 CPU 口径（最快原语实测的单核吞吐 ÷ 核数，和最长串行部分取大）；容器里不能有 GPU 设备；绑一个 NUMA 节点的物理核加超线程，题面写明核数。

### B 上限和基线强度

- **B1 T_ref 和 T1 怎么测。**
  - T_ref：参考的生产配置，跳过 warmup 和编译，取 ≥ 3 个固定窗口，多卡取最慢的卡；在整机（至少计时卡所在的 NUMA 半边）空闲时测；写出窗口值和出处。
  - T1：按阶段算，每阶段 max(计算 / 实测峰值, 访存 / 实测带宽, 通信 / 实测 busbw)，段间相加（`scripts/bound.py`）。峰值用 `scripts/peaks.py` 在同一台机器、同一种卡上测，先连跑几秒等时钟稳定。
  - 被规则冻住的部分（只收 N0 时的 GEMM、写死精度的部分、判卷规定的串行部分）用参考 kernel 的实测时间（`frozen_time`），不按峰值算。
  - T_ref / T1 < 2 就停（规程 B 的准入）；还要在报告里写 T_ref / T1 的组成：哪几个阶段贡献了大部分上限，避免一个算松了的阶段撑起整个上限。
- **B2 开关阶梯怎么测。** 只用规则允许的现成开关（不写代码），最多叠 5 个，每加一个测一次，记每一步和最好组合的 L。和 T_ref 同一套计时、同一台空闲机器。ln L / ln(T_ref / T1) > 1/3 时，请 owner 选：把这些开关并进参考（参考变强，重测 T_ref、T1）或拒题。阶梯的具体开关和数值是验题数据，**只放 `vetting/<题名>/`，不进题面、镜像，也不对外公开**（等于半个答案）。
- **B3 A/A 要在判卷自己的计时框架里再测一次。** B 段用最小计时脚本测的 A/A 可能偏乐观：判卷放进被测进程里的额外工作（采样、记录）、每个进程固有的速度差，都会让真实 A/A 变大。C 段判卷搭好后，用判卷的 `time` 命令重测 A/A：
  - ≤ 3%：通过；
  - > 3%：先找噪声来源（采样放到判卷自己的进程里、绑核、关掉随机路由策略）；还是超就停下请 owner 定（例如最终评测改成多次运行取最快、门槛相应抬高），不要自己放宽。
- **B4 饱和线。** 吃掉的对数空间 h = ln(加速比) / ln(T_ref / T1)。已知的任何成绩（包括题面有提示的内部尝试、上游的快版本）h > 80% 时，这道题（或这个子题）有饱和风险：B 段结束时报告里写出来，请 owner 决定 C 段还做不做。D 段最好成绩 h > 80% 判饱和（规程 D 的准入）。

### C 打包和验判卷

- **C1 判卷分档 N0 / N1。**
  - N0：exact items（步数、超参、每卡数据行、形状和 dtype、RNG 指纹……）全部相同，张量逐位相同。
  - N1：exact items 全部相同，张量不逐位，但统计门判等价。
  - 改了参数或优化器状态的 dtype 等精度变化：不收（INCORRECT），不管数值多接近。
  - 参考自己就不能逐位复现（两次确定性记录不一致，例如用了没有确定性实现的 kernel）时，这道题**只有 N1 档**，打分卡和题面都写“只收 N1”，不要写“N0 + N1”。
  - 统计门对逐位一致的候选照样跑（生产配置），不能因为 N0 就跳过。
- **C2 必拒和必过对照。**
  - 每道门至少一个必拒对照，要让门**判错**（INCORRECT），不能让程序崩（ERROR）；改动要落在配方真正跑到的代码路径上。
  - 必过（合法改写）至少 3 种。某个必过被拒时先查是谁错了：判卷错了就修判卷；改写其实改变了输出（例如改了分片方式，下游阶段读数据的顺序跟着变，某个按顺序取值的步骤给出了不同结果），那它就是必拒，改记为必拒，再换一个真正合法的改写。不许为了让它通过而放宽门。
  - 启动准备里也放对照（每道门一个必拒、一个必过），在真实输入上跑。
  - 具体的对照清单和改法是判卷内部信息：放 `vetting/<题名>/` 和判卷代码里，不写进题面，也不对外公开（发布分支只保留题目本身需要的最少对照）。
- **C3 误拒率。** 用每个合法改写的 z 值（偏差 / σ）估各端点的相关性 ρ，再用 `scripts/frr.py` 模拟整体误拒率，≤ 1%。超了：减少或合并端点、换对改写不敏感的端点，或者事先写进判卷的“第二种子”规则（统计门不过时换一个新种子再判一次，两次都不过才拒；必拒对照在这条规则下必须仍然被拒）。不许为某个候选临时加。
- **C4 nop 冒烟。** `-a nop` 跑完整准备加最终评测，reward 必须为 0（no_benefit / UNAVAILABLE）。没改动的树判最终评测，加速比必须低于门槛。nop 不读题面，改了题面不用重跑 nop，但 D 段用的包必须带新题面。
- **C5 留出集不能被反推。** 最终评测的计时窗口和统计门的种子用 agent 没见过的同分布数据，参考也在同一段留出数据上测。
  - 开发集和留出集**不能**来自同一个固定种子的同一次抽样：agent 有网，能从开发集的文件名反推出种子，提前下载留出文件、算好答案，终判时查表。
  - 留出集用不可复现的随机源（例如 `secrets.SystemRandom`）抽，名单只放 root 能读的地方，不进 git、不进镜像、不进报告正文；agent 能看到的清单不写种子和抽样方法。
- **C6 统计门的基准用参考包，不用单次冻结。** 统计门的带宽（参考自己的分布）从一次启动里冻结的少量样本估出来时，估计本身的误差很大（样本少时，标准差的估计可以差几十个百分点）。不同机器各自冻结一次，带宽就各不相同，同一个候选在一台机器上过、在另一台被拒。
  - 规则：所有机器都对**参考包里冻结的**基准判（包由一次独占、低噪声的完整准备产生，见 `vetkit/`）；本机冻结的值只作交叉核对，偏离超过阈值时报警或拒绝启动。
  - 设计统计门时优先选标准误能直接算出来的统计量，带宽由合法改写标定，而不是靠少量窗口估。
- **C7 计时核对的 band 只核机器，不当候选门槛。** 每次 trial 启动、每次判卷前，用参考跑一次计时和包里冻结的值比（band），这一步只回答“这台机器、这组卡和建包时是不是一样快”。
  - band 按参考自己每个进程的速度分布定：例如一台机器上 N 次参考运行里，用这个 band 时 0 次超出。
  - 它不是候选的门槛。候选的门槛是 gate 1：最终评测里现场按 参考 → 候选 → 参考 测，max(1.02, 1 + 2 × 参考的波动)。
  - band 核对的字段必须是一个数（不是窗口列表）。
- **C8 判卷前清理截止时遗留的状态。** agent 到点被杀时，可能留下确定性命名的状态：GPU 共享或进程间通信用的守护进程和它们的控制目录、锁文件、`/dev/shm` 里的段、记着已死 pid 的文件。候选自己的安全逻辑看到这些会拒绝启动，最终评测报 ERROR，这不是模型的错。
  - 规则：最终评测之前，判卷先清掉截止时遗留的这类状态，再启动候选。要清的路径由题目的判卷列出（通用的有这类守护进程的控制和日志目录、`/tmp` 下的锁和 pid 文件），写在 `tests/test.sh` 或 `verify.py` 里、`bench.py check --final` 之前，以 root 执行；候选的源码树和候选环境不动。
  - Harbor 的 shared verifier 在 agent 的原容器里判，这条规则管的就是它。在干净容器里从提交物重判（`vetkit/bin/refpack.py judge`）本来就没有遗留状态。
  - 已经因此 ERROR 的格子，按这条规则重判。
- **C9 模板里的几个坑**（来自不同题，模板已修）：
  - 判卷用的 GPU 锁文件由 root 建时要 `chmod 666`，否则 agent 用户打不开；
  - 容器 PID 1 是 `sleep infinity` 时没人收僵尸，判卷的“候选进程在 SIGKILL 后是否还活着”检查会把僵尸当成活进程：检查要把状态 Z 的进程当作已退出，或者给容器一个会收僵尸的 init（Compose 的 `init: true`）；
  - 挂进容器的 `/tmp` 可能是 755，entrypoint 要先 `chmod 1777 /tmp`；
  - 从 `python:*-slim` 起的镜像没有 `/usr/bin/python3`，脚本要找 `/usr/local/bin/python3`；
  - 镜像里的 CUDA forward-compat 库只在比宿主机驱动新时才加载，比驱动旧时加载会报 error 803；
  - 有的 Compose 版本解析不了 `!reset` 标签，override 文件里不要用。
- **C10 判卷进程的 PATH 和它调用的工具必须是 root 拥有、agent 不可写的。** verifier 以 root 运行。镜像为了让 agent 的命令默认用候选环境，常把 agent 可写的目录（例如 `/opt/candidate-env/bin`）放在 `PATH` 最前；verifier 原样继承这个 `PATH` 时，它按名字调用的程序就不一定是系统的那个。
  - verifier 一开始就把继承来的 `PATH` 过滤成只剩 root-only 的目录：目录本身和到它的每一级上级都归 root、组和其他人不可写；符号链接逐级解析，链接所在的目录也要满足这个条件（agent 可写目录里的链接，指向哪里都不算）。再补上系统目录。调用外部程序用这个 `PATH` 解析出的绝对路径（程序本身也要 root-only），或者直接写绝对路径；`test.sh` 里的解释器也写绝对路径。
  - 能从 `/proc` 得到的不调外部程序：找、杀 agent 用户的进程读 `/proc/<pid>/status` 的 Uid（僵尸不算，见 C9），不用 `pgrep` / `pkill`。
  - verifier 以 agent 身份运行判卷和 `git`（`runuser -u agent`）时，也只传这个过滤后的 `PATH`，并设 `GIT_CONFIG_GLOBAL=/dev/null`（git ≥ 2.32），不读 agent 家目录里的 git 配置。判卷自己调用的工具（`nvidia-smi`、`git`……）因此也不会是 agent 的；候选的运行由判卷自己把候选环境放回 `PATH`。判卷用的解释器同样要 root-only。
  - 以 agent 身份对 agent 的仓库跑完 `git`（存档提交历史）之后，再清一次 agent 用户的进程：仓库自己的配置也能启动程序。
  - `vetkit/bin/onboard_check.py` 查 `tests/` 里按名字调用常见程序的地方，镜像的 `PATH` 含有给了 agent 的目录时给警告；`vetkit/container/entry.sh`（`refpack.py judge`）自己的命令只用系统目录，交给 `test.sh` 的 `PATH` 也去掉了不是 root-only 的目录。但 Harbor 的 shared verifier 不经过 vetkit：这条规则要在题目自己的 `verify.py` 里做到（`vetkit/examples/tasks/nanochat/tests/verify.py` 是写法示例）。

### D pilot

- **D1 半机独占终判。**
  - agent 阶段：可以和别的格子共用一台机器（各占一个 NUMA 半边的卡和核）。
  - 最终评测（参考 → 候选 → 参考 的计时）：至少独占计时卡所在的 NUMA 半边（这半边的卡和核上不跑别的东西）；另一半照常跑 agent，或判它自己那一半。成绩注明“半机独占终判”。
  - 建参考包、B 段的计时：独占整台机器。
  - 另一半释放大块显存时，驱动的全局锁偶尔会让一次计时卡住 10–16 秒。终判各侧取最快、参考差大时补测、最多 3 次尝试，一般能吸收；一格 3 次里 ≥ 2 次 INVALID，或者判不出来，就改成整机独占重判。
  - 可疑结果（偏离保护触发、参考三次差得大、和复本差得多）整机独占再判一次，记复判成绩。
- **D2 区分度。** 准入照规程 D：最好成绩 h 在 20–80%；没有归因为 judge 的失败；多格时复本差 < 模型差，模型先后和公开榜一致。最好成绩 < 1.3× 要写原因。pilot 看成绩随时间的曲线：例如 5 小时内已到最终成绩的 90%，全量批次可以考虑缩短预算（由 owner 定）。
- **D3 每个模型用和公开榜一致的 harness。** reasoning effort 用最高档。DeepSeek 系列统一用 Codex CLI（OpenAI 兼容接口，key 换成 DeepSeek 的），不用自写的 harness。harness 和版本写进每格的记录。
- **D4 每个非 PASS 的格子都归因**（model / judge / infra）。C8 那种截止遗留状态造成的 ERROR 是 infra；先按规则修，再重判，不算模型失败。

### E 收尾

- **E1 复判。** 最好的提交用 final 重判 2 次，都要 PASS（规程 E）。复判要在干净容器里从提交物重建（同一个镜像、参考包只读、提交物以 agent 用户放回原位、不联网），不要在 agent 的原容器里重跑。`vetkit/bin/refpack.py judge` 就是这条路径。
- **E2 记版本。** 判卷哈希（判卷工作区在准备之前的 sha256）、镜像 digest、上游 commit、参考包 key。判卷一改，以它为 key 的参考包失效，已存档的提交用新判卷重判。
- **E3 对外公开的范围。** 题目本身（task.toml、题面、判卷、启动准备）可以公开；`vetting/` 下的东西（上限、阶梯、热点、对照清单、留出集名单、各模型的 trace 分析）在题目的公开批次跑完之前都不公开，跑完以后也只公开汇总数字。
